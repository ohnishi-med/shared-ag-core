# 論理構成とセルフレビュー

読むタイミング: 初稿作成時、および構成の大幅な手直し(圧縮・Figure差し替え等)をするたび。

症例報告は「事実の時系列的な羅列」ではなく、「臨床的疑問→検証→結論」という**診断としての論理フロー**で書く。以下の観点を、初稿作成時および大きな構成変更のたびにセルフチェックする。

- **Known→Unknownの順序**: Background/Abstractの導入部は、確立している知見(Known)を積み上げ、最後に知見のギャップ(Unknown)を置いて締める。ギャップの文をKnownの記述の途中に前倒しで挟むと、その後に続くKnownの記述が浮いてしまい、論理が逆転して見える。
- **原因→発見(エビデンス)→反復確認による一般化の順序**: 症例提示で「一貫して改善した」のような一般化した結論を先に述べてから根拠となる具体的エピソードを出し、さらに末尾で同じ結論を繰り返す、という冗長な構成にしない。「なぜその介入が必要だったか(原因)→象徴的な1エピソード(発見)→その後のセッションでの再現性(一般化)」の順に一度だけ流す。
- **診断としてのフロー**: 症例提示は理想的には次の流れを意識する: ①臨床的問題の提示 → ②通常想定されるデフォルト仮説 → ③その仮説を裏切る転換点となる所見 → ④代替の作業仮説 → ⑤仮説の客観的検証(検査・測定) → ⑥治療反応による反復確認 → ⑦代替診断の除外 → ⑧到達した解釈とその限界 → ⑨転帰。Discussionで鑑別診断を論じるのは標準的だが、Case Presentation側も「事実の提示」だけでなく、この流れに沿った記述にする。
- **Case PresentationとDiscussionの解釈的記述の境界**: 「Case Presentationには解釈を一切書かない」という単純化は、実際の掲載論文の慣行と一致しない。同一ジャーナルの掲載済みCase Reportを複数本確認すると、Case Presentationにも診断へ至る推論(例:「〜の所見からXと臨床診断された」「〜による閉塞と判断された」「〜に起因すると考えられた」)は普通に含まれている。境界線は「解釈の有無」ではなく「何についての解釈か」で引く: **その症例で何が起きたか・何と診断されたかを述べる推論はCase Presentationに書いてよい**。**論文独自の中心的な機序仮説を支持するための、対立仮説の個別排除・反証型の議論(例:「これは〜という説には反する」「〜が主因ではないことを示唆する」)はDiscussion専用**。判断に迷ったら「これはこの論文オリジナルの主張を組み立てる論証か、それとも症例の診断そのものの提示か」を自問する。
- **見出し番号の一貫性**: サブセクションに番号(4.1, 4.2等)を振る場合、文書全体で一貫させる。構成を圧縮・再編した結果、一部のセクションだけに孤立した番号(対応する上位番号が存在しない)が残っていないか確認する。番号を使わない方針にする場合は全セクションから外す。

**大きな構成変更(Figureの差し替え、セクションの圧縮・統合等)を行った後は、原稿全体を通しで読み直すコヒーレンスチェックを必ず実施する。** 差し替え・圧縮作業は特定の段落にしか目が行かないため、以下のような追従漏れが起きやすい:
- Figureを差し替えたのに、Abstract・Conclusions・Discussion・Limitations中の古い言及("a single CT study" 等、差し替え前の対象を指す表現)が更新されていない
- Tableに新しい行(検査項目等)を追加したのに、Abbreviations一覧とそのTable自身の脚注用語集の両方に追加し忘れている
- Timelineの表に、後から判明した重要イベント(同日に実施された別の検査等)が反映されていない
- 本文中の相互参照("see Discussion 4.2"等)が、見出し番号や節構成の変更後も古い番号のまま残っている
